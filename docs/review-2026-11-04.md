## A. Defects found in my own Phase 0 design (all fixed in rev 2)

| # | Severity | Where | Defect | Evidence | Fix |
|---|---|---|---|---|---|
| A1 | **High: security** | §9.4 | Tenant constraints were attached via `customer_admin`'s profile. A user the tenant creates **without** that role escapes them completely: `max_memory_usage = 0`, `max_threads = 64`, and `database_replicated_allow_only_replicated_engine = 0` were all accepted. | lab §2.1 | Constraints move into the server `default` profile; provider profiles relax explicitly. Re-tested: the escape is closed. |
| A2 | **High: data safety** | ADR-0007 | It relied on a `Replicated` database to prevent unreplicated tables. A plain `MergeTree` inside a `Replicated` DB is silently created unreplicated by default. Also, tenants can't create `Replicated` databases at all once engine grants are on (database engines aren't grantable). | lab §2.2, §2.6; script | `TABLE ENGINE` grants are the primary fence (tested), with `allow_only_replicated_engine` `const` in the default profile as a second layer (tested). `Replicated` databases come via the API. |
| A3 | **High: contradiction** | §12 / §9.5 | Backups used an EKS Pod Identity role on the server pods, but the baseline forbids ServiceAccount tokens and the egress policy blocks link-local (where the Pod Identity agent lives). It also exposed cloud credentials to tenant SQL. | design review | No ambient credentials in pods. Per-backup STS credentials go in a provider-only named collection (tested: the token is sent, tenants are denied, secrets are `[HIDDEN]` in logs). |
| A4 | **High: correctness** | §8.3 | The label-integrity rule said "only the operator's ServiceAccount may create labelled pods", but pods are created by the **StatefulSet controller**, so as written the rule would have blocked every ClickHouse pod. The toleration fence also covered dedicated taints only, not the shared pool. | design review | Rules split: StatefulSets (operator SA), pods (statefulset-controller plus ownerReference), and a toleration fence for every pool taint. |
| A5 | High: security | §9.3 | Grants used the pre-26.x `SOURCES` names. On 26.8, source access is `READ/WRITE ON <source>`, `executable()` is gated by `TABLE ENGINE ON Executable`, and `SELECT ON *.*` exposes `system.zookeeper`. | script | Grant list rewritten with partial revokes; each grant tested. |
| A6 | Medium: config | §9.3, ADR-0007 | `table_engines_require_grant` was given as a top-level server setting. At top level the server **refuses to start**; it belongs under `access_control_improvements`. | lab §2.6 | Corrected. New F-23: CI boots every rendered config. |
| A7 | Medium: product | §1, §10 | Async inserts were "to verify". They're **on by default** (`async_insert = 1`, `wait_for_async_insert = 1`). | script | Pinned explicitly; `wait_for_async_insert` `const` on shared tier; M5 tests quorum together with async inserts. |
| A8 | Medium: pricing | §7.3, ADR-0004 | Arithmetic errors: `s-2` compute is about $113/month, not $76, and `s-8` about $451, not $305. **Keeper overhead at `s-2` is about 33%, not "about 50%"**, the figure I gave you in the Phase 0 summary. The dev row also used a 3-node Keeper, contradicting the recommendation. | recomputed | Table corrected; `s-4` row added; dev shown with a single-node Keeper. |
| A9 | Low | §9.4 | The stated reason for `settings_constraints_replace_previous` was backwards: it *allows* later profiles to replace constraints. It's safe because tenants can't create profiles beyond their own constraints (tested). | script | Reworded. |
| A10 | Low | ADR-0002 | "About 100 tags" counted peeled refs. | – | "Dozens of releases". |
| A11 | Low | A8, ADR-0005 | Client SNI was unverified. | lab §2.5 | `clickhouse-client` 26.8 sends SNI (tested); other clients are still open. |

Things I reviewed and left unchanged: the control plane / data plane split, the Engine interface, PDB and rolling gates, readiness that ignores read-only status, the Keeper topology, the dedicated anti-affinity with `namespaceSelector: {}`, the disk-full handling, and the networking choices.

## B. Review of the AI query optimizer

Overall: the code is well structured. It has a pluggable registry, strict JSON parsing, an anonymised judge, a single-statement allow-list, and separate reader and writer accounts in its deployment guide. Its safety model is sound for Postgres and MySQL, where `CREATE INDEX` is synchronous. **On ClickHouse it has three behaviours that make god mode unsafe or ineffective**, all reproduced against 26.8.34:

| # | Severity | Finding | Evidence |
|---|---|---|---|
| B1 | High | God-mode verification measures before the skip index exists, because `MATERIALIZE INDEX` is an async mutation. The run reports `applied; plan cost 2443.0 -> 2443.0`. | lab §2.3 |
| B2 | High | Auto-rollback can't work during materialisation: `DROP INDEX` is refused while the mutation runs. | lab §2.3 |
| B3 | High | LLM rewrites containing `url()` (or other table functions) pass `is_read_only_query` and get EXPLAINed. On ClickHouse, EXPLAIN performs the HTTP request (5 hits observed), so this is SSRF from the optimizer host, using whatever grants its account has. | lab §2.3; script |
| B4 | Medium | An empty `EXPLAIN ESTIMATE` (non-MergeTree source) becomes cost 0.0, which the judge sees as a perfect rewrite (354 → 0.0). | lab §2.3 |
| B5 | Medium | `redact_literals` protects LLM prompts but **not reports or notifiers** (the raw literal is in the report JSON). | lab §2.4 |
| B6 | Medium | `qopt init` is broken in the committed repo: `templates/config.yaml` is excluded by `.gitignore`, so 2 of 75 tests fail. | `pytest`: 73 passed, 2 failed, 6 skipped |
| B7 | Low | EXPLAIN executes scalar subqueries, so the "never executes anything" claim doesn't hold on ClickHouse. It's bounded by `statement_timeout_s` → `max_execution_time` (already implemented). | script |
| B8 | Low | The licence is declared MIT but there's no LICENSE file. | repo listing |

The integration ([ADR-0008](adr/0008-query-optimizer-integration.md)) **doesn't depend on any of these being fixed**:
* B1 and B2: analysis only; applying goes through our workflow, which tracks mutations.
* B3: the optimizer user has no source grants (tested: denied).
* B4: our validator re-measures, and treats empty estimates as unknown.
* B5: query text is dropped on ingest.
* B6: we generate config at runtime.

The upstream fixes are listed as U1–U8 in ADR-0008.
